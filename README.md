## Анализ и рефакторинг
1. Какие проблемы были в исходной реализации списания?
   Race Condition (Состояние гонки): Чтение баланса и создание транзакции списания не были атомарными. 
   Параллельные запросы могли одновременно увидеть положительный баланс и списать бонусы в минус.
   Отсутствие идемпотентности: Поле requestId не учитывалось. Повторные запросы приводили к дублированию списаний средств.
   Некорректный расчет баланса: Старая логика не учитывала срок годности начислений (expires_at) и не вычитала уже совершенные траты.
   Обработчик очереди был "заглушкой" без бизнес-логики и не вносил изменений в БД.
2. Какие проблемы при одновременных запросах вы устранили и как именно?
   Проблема: Отрицательный баланс при параллельных вызовах.
   Решение: Внедрена транзакция Sequelize с уровнем изоляции и Row-level Locking (SELECT FOR UPDATE). 
   Использование User.findByPk(id, { lock: t.LOCK.UPDATE }) блокирует строку пользователя. 
   Все параллельные запросы идут по очереди и видят актуальный остаток после завершения предыдущей транзакции.
3. Какие обязательные правила корректности вы обеспечили на уровне БД и на уровне кода?
   На уровне БД: Атомарность операций через транзакции. Исправлена область уникальности request_id: 
   создан составной уникальный индекс (user_id, request_id) для корректной работы идемпотентности в рамках разных пользователей.
   На уровне кода: Валидация входных данных (целые положительные числа), 
   строгая проверка amount при повторе requestId (возврат 409 Conflict) и фильтрация просрочки по времени сервера.
4. Как реализована защита от повторного одинакового запроса (duplicate request)?
   Реализован механизм Idempotency Check. При получении requestId (из заголовка или body)
   система проверяет наличие записи в таблице транзакций для данного пользователя.
   Проверка вынесена внутрь транзакции после блокировки пользователя, 
   что гарантирует детерминированный результат даже при одновременном поступлении дубликатов.
   Если запись найдена и данные совпадают — возвращается duplicated: true.
5. Как обеспечено, что просроченное начисление (expired accrual) не участвует в балансе?
   В методе getUserBalance (и в сервисе списания) добавлен SQL-фильтр: expires_at: { [Op.gt]: new Date() }.
   Формула баланса: SUM(active_accruals) - SUM(all_spends).
6. Как реализована надежная обработка очереди?
   Защита от дублей задач: Используется предсказуемый jobId: 'expire-accruals' для запрета накоплений одинаковых заданий в Redis.
   Устойчивость (Retry): Настроено 3 попытки (attempts: 3) с фиксированной паузой в 1000мс (backoff) для обработки временных сбоев БД.
   Бизнес-эффект: Воркер создает компенсирующие транзакции type: spend с уникальным ключом expire:<accrual_id>.
   Это обеспечивает идемпотентность: повторный запуск воркера видит существующее списание и не дублирует его.
7. Какие компромиссы вы приняли в рамках ограничения 4–6 часов?
   Интеграционные тесты: Реализовал покрытие только крит сценариев (Race Condition, Idempotency) через HTTP-вызовы без unit тестирования методов.
   Производительность воркера: Выборка просроченных записей производится общим списком. 
   В хайлоад можно внедрить пагинацию при обработке просрочки.
   Архитектура: Бизнес-логика воркера оставлена в слое очередей для упрощения.
